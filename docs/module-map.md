# Module map

The full contract of each Gradle module: what it owns, what it must not do, and why each
dependency edge exists. `CLAUDE.md` carries the one-line summary; this file is the reference.
Update both when a module or an edge changes. Decision rationale lives in `docs/adr/`.

## Modules

Thirteen Gradle modules.

- `passes-core`: pure Kotlin/JVM. Parser, model, signature verifier, `.strings` parser, `TelemetryGuard` interface, `PassBundleReader`, `PassEncoder` and `PngHeader`. `PngHeader` is the one reader of a PNG's IHDR chunk and the PNG test for pass images: the parser keeps a pass image only when it reads, and `passes-ui` applies the same read before a pass image reaches the platform decoder. `PassBundleReader` is the outer-layer reader for `.pkpasses` bundles: cumulative caps via `BundleConfig`, typed `BundleReadResult`, entries handed to the caller as bytes for `PassParser`; it never opens an inner archive. `PassEncoder` turns a parsed `Pass` back into an unsigned `.pkpass` (ADR 0001 D8). No Android framework dependencies.
- `passes-document-core`: pure Kotlin/JVM (package `is.walt.passes.document`). The kind-agnostic document model: sealed `Document` with `PdfDocument` / `ImageDocument` arms, `DocumentId`, `DocumentRejectedKind`, the PDF header sniffer (`isPdfHeader`), import config, and the `DocumentTelemetryGuard` interface. No Android framework dependencies.
- `passes-barcode-core`: pure Kotlin/JVM. The trust-claim-bearing ZXing symbol decode (`decodeLuminance(LuminanceSource)`) and the symbology allowlist (`ROSTER_BY_ZXING_FORMAT`, `DECODE_HINTS`). One decode implementation shared by the isolated still-image path (`passes-barcode`) and the in-process live-camera path (`decodeYPlane`). Depends on `passes-core` (for `ScannableFormat` / `BarcodeDecodeResult`) and adds `com.google.zxing:core`. No Android framework dependencies.
- `passes-isolation`: Android-only. Shared isolated-worker plumbing for `passes-pdf`, `passes-barcode`, `passes-image` and `passes-document`: the memfd `PfdFactory` (bytes to a sealed in-RAM PFD), the bind/teardown session facade (`IsolatedWorkerSessionFactory` -> `ConnectResult` -> `IsolatedWorkerSession`, parameterized over the per-worker service class and typed binder client), `readBoundedBytes` (offset-independent bounded fd read; the cap is the caller's) and `rasterReplyFits` (the pure predicate host-side clients `PdfRendererClient` and `ImageDecodeClient` use to validate a sandbox's raster reply before allocating from it; the caps are the caller's). Declares no service; each consumer declares its own `isolatedProcess` service. Mechanism only: no trust-claim-bearing policy, and the per-worker contract and result shape stay in the consumer.
- `passes-image-decode`: Android-only (needs `android.graphics`, so not a `-core` module). The single bounded `ImageDecoder` primitive: `decodeBounded(rawBytes, policy)` applies the caller's header gate before allocation, decodes an accepted image at a whole-number division of its size that fits the caller's box (never enlarged), ends the decode from the header listener on reject so a refused image is never decoded, and folds the failures the platform decode raises into the caller's rejection type (the `OutOfMemoryError` fold is opt-in via a nullable callback). Consumed by `passes-barcode` (isolated still-image decode, software allocator, OOM contained), `passes-ui` (in-process pkpass display, PNG only, default allocator, downsampled to the caller's bounds, OOM propagated) and `passes-image`. Mechanism only: caps, output box, format allowlist and rejection taxonomy (`R`) stay with each consumer.
- `passes-pdf`: Android-only. Isolated-process PDF renderer service (ADR 0005 D3). Wraps Android's `PdfRenderer` behind a hand-rolled binder with no extraction surface. Binds its service through `passes-isolation`.
- `passes-barcode`: Android-only. Isolated-process barcode/QR-from-image decode service. The `BarcodeImageDecoder` facade takes an image source over a bind, decodes inside a permissionless sandbox, and returns only `{payload, ScannableFormat}` (pure `BarcodeDecodeResult` from `passes-core`); never a Bitmap or source bytes. Holds only the `Bitmap -> RGBLuminanceSource` adapter and delegates the symbol decode to `passes-barcode-core`. No classification or validation here.
- `passes-image`: Android-only. Isolated-process image-decode service. `ImageDecodeService` decodes original user-image bytes inside a permissionless sandbox and returns only a bounded ARGB_8888 raster to the host over `SharedMemory`; never the source bytes, never a host-process codec run. Mirrors `passes-pdf`'s `PdfRendererService` (hand-rolled binder, raster over `SharedMemory`) but with one "page", no PDFium and no SDK-34 floor (rests on `ImageDecoder` at the repo-wide minSdk 28). Binds its service through `passes-isolation` and delegates the bounded decode to `passes-image-decode`. Owns its own reject taxonomy `ImageDecodeRejectedKind` (`NotAnImage` / `OversizedAtImport` / `DimensionsTooLarge` / `DecodeFailed` / `DecoderUnavailable`), deliberately not flattened into the PDF `DocumentRejectedKind`. Exposes the `ImageDecodeBinder` contract (consumed by the display surface the way `passes-document-ui` consumes `PdfRendererBinder`) and a bind-per-call `BoundedImageDecoder` facade for the import path.
- `passes-document`: Android-only. The document-import orchestrator. `DocumentImporter` magic-byte-sniffs PDF vs image (`isPdfHeader` from `passes-document-core` plus `sniffImageFormat` here) and branches to the isolated backend: PDF to `passes-pdf`'s `PdfImporter` / renderer service, image to `passes-image`'s `BoundedImageDecoder` sandbox. When the caller opts in with a `confirmBarcode` hook, the image branch also runs `passes-barcode`'s still-image decoder (composite barcoded image). The single bounded read materializes the bytes once into a sealed memfd PFD (ADR 0005 F.1) via `passes-isolation` and hands it to whichever backend wins, so a one-shot fd source is read exactly once. Folds each backend's outcome onto a unified `DocumentImportResult` whose reject arms reuse each backend's taxonomy verbatim (`PdfRejected(DocumentRejectedKind)`, `ImageRejected(ImageDecodeRejectedKind)`), with no third reject enum; `Unrecognized` and `StorageHandoffFailed` are the two kind-agnostic arms. It holds no decode or render code and declares no service, so the isolated surface stays auditable in the backends. Storage is wired through a `persist(DocumentPersist)` callback, not a `passes-storage` dependency, mirroring `PdfImporter`.
- `passes-storage`: Android-only. SQLCipher with Keystore-sourced key, Android Auto Backup exclusion, irreversible deletion. The `documents` table covers PDF and image (schema v6): a `format` discriminator column (`pdf`/`png`/`jpeg`/`webp`) plus nullable `width_px`/`height_px`; `insertDocument` takes a sealed `DocumentInsert` (`Pdf(pageCount)` | `Image(format, widthPx, heightPx)`); `loadDocumentBytes` / `loadDocumentThumbnail` are kind-agnostic. The original `.pkpass` archive bytes are retained at import in the `pass_archives` sidecar table (schema v8): `upsert(pass, signatureStatus, archiveBytes)` requires them (capped at `PassArchiveBounds.MAX_BYTES`, rejected as `PassRejected(ArchiveEmpty | ArchiveOversized)`) and `loadArchiveBytes(id)` returns them byte-exact (`null` for rows imported before v8 or via the deprecated two-arg `upsert`). Only that path reads the sidecar; `passes` / `load` / `summaryOf` never touch it.
- `passes-ui-core`: Android + Compose. Small shared substrate for both UI modules: `ArgbColor`, `Color` conversion, the `isolated()` BiDi (FSI/PDI) helper, and the `faceIsTinted` predicate (the shared gate deciding whether a consumer-supplied face tint is taken; `isSpecified` alone is true for `Color.Transparent`). No trust-claim-bearing surfaces; exists so `passes-ui` and `passes-document-ui` do not depend on each other.
- `passes-ui`: Android + Compose. PKPASS surfaces only: pass front/back composables, B3 URL confirmation sheet, expired badge, bounded image rendering, `PassesTheme` / `PassesSemantics`. Themable via tokens passed in by the consumer.
- `passes-document-ui`: Android + Compose (package `is.walt.passes.document.ui`). Document surfaces (PDF and image): `DocumentView` (a dispatcher over sealed `Document`: PDF to swipeable pager, image to single image), `FullScreenDocumentView`, `DocumentTrustCaption`, `DocumentTheme` / `DocumentSemantics`. Depends on `passes-pdf` (`PdfRendererBinder`), `passes-image` (`ImageDecodeBinder`) and `passes-document-core` (`Document`); themed through its own `LocalDocumentSemantics`, not `PassesSemantics`. The trust caption (one verbatim `DocumentTrustCaption`) docks on `FullScreenDocumentView` for every arm and cannot be dropped there; inline `DocumentView` draws none, and the host carries provenance via its own "Pass type" row (ADR 0005 D5.T).

## Dependency rules

- `passes-core`, `passes-document-core` and `passes-barcode-core` have no Android framework dependencies (KMP-friendly).
- `passes-storage`, `passes-pdf`, `passes-barcode`, `passes-image`, `passes-ui` and `passes-document-ui` are independent peers. The permitted exceptions are `passes-document-ui -> passes-pdf` and `passes-document-ui -> passes-image` (the document display surface needs `PdfRendererBinder` and `ImageDecodeBinder`). `passes-pdf` and `passes-image` never depend on each other.
- `passes-document` sits above `passes-pdf`, `passes-image` and `passes-barcode`, and is the only module that depends on all three, by design: the sniff-and-branch orchestration is one audited surface rather than peer-to-peer edges. The `passes-pdf` and `passes-barcode` edges are `implementation` (their types do not escape the public surface); `passes-image` is `api`.
- `passes-storage` has one test-only dependency on `passes-document-core`, so `DocumentBoundsParityTest` can hold `DocumentBounds` equal to the import caps.
- `passes-barcode -> passes-barcode-core -> passes-core`: the Android module keeps only the platform `Bitmap` adapter, while the pure-JVM decode and its roster allowlist live in `passes-barcode-core` so the still-image and live-camera paths share one implementation. `passes-barcode-core` adds no edge between the peers.
- `passes-pdf`, `passes-barcode`, `passes-image` and `passes-document` depend on `passes-isolation` for the shared bind/memfd plumbing (`passes-document` to materialize the sniffed bytes into one memfd PFD). `passes-isolation` depends on nothing in this repo, so it adds no edge among them.
- `passes-barcode`, `passes-ui` and `passes-image` depend on `passes-image-decode` for the shared bounded `ImageDecoder` mechanism. It depends on nothing in this repo, so it adds no edge among them.
- `passes-ui` and `passes-document-ui` both depend on `passes-ui-core`, never on each other.
- Decisive constraint: walt-android consumes this code directly; trust-claim-bearing logic lives only here, never reimplemented in walt-android.
